Auto-Retail Challenge Refresher

A walkthrough of every step of the Auto-Retail scenario in the Splunk Agent Observability (SAO) Customer Challenge, with reference answers to check your work.

How to use this page Do each step yourself first. Then open Reference answer to compare. The answers are examples, not the only right ones. A real team writes every cell in its own words, because a coach will ask you to explain each line and setting.
This is an unofficial study guide It is not an official Splunk page and it isn't a replacement for the product docs at agent-observability-docs.splunk.com. Values shown as <like-this> are placeholders. Never paste real keys or passwords into a shared page.

The scenario in one minute

You are the solutions engineer for an automotive retail marketplace. Their dealer-website car-shopping assistant is a four-step LangGraph agent (intake, route, resolve, write). Their feared failure is a grounding failure between two of their own systems: a brochure says a model has a hands-free driving package, but the inventory record for the specific vehicle does not, so the shopper is told the car has a feature it doesn't.

In the starter agent this is the planted failure fabricated_citation. With it on, the agent adds a fake brochure BR-999 that says every Meridian trim has hands-free driving, while inventory record V-2003 (the EX trim) says it doesn't.

Who you present to

RoleCares about
BuyerToken spend, and one governance view across business units
Head of ML"Is this calibrated?" about any evaluator you show
Technical evaluation ownerRuns a human-calibrated LLM-as-judge today and wants the loop automated; has seen the tour
New stakeholderGovernance, probably

The win: a custom judge grounded against the inventory record, with a rationale the head of ML would accept, plus honesty about what the tokenomics module does and doesn't attribute.

The path at a glance

  1. Read the scenario and mark what the customer actually said.
  2. Fill the design worksheet (3 to 5 rows, each starting with a quote).
  3. Generate the agent with the build skill and prove the planted failure.
  4. Instrument it: callback, then metadata, then the first trace.
  5. Evaluate: a custom LLM-as-a-judge evaluator on the stream.
  6. Act on the failure: an alert and a runtime control.
  7. Validate: clean traffic stays clean, the failure is caught and stopped.
  8. Write success criteria and present a 10-minute customer meeting.

Rules of the road

  • Spend your time on the product and the customer, not on the agent. It is capped at four steps and four tools.
  • You may use Claude Code or Cursor to help write the instrumentation, but you must be able to explain every line.
  • If the scenario says the customer didn't ask for it, it isn't in your demo.
  • Don't use the demo-builder skill during the challenge. It is for afterwards.

5. Add the callback

One object, attached to the graph call, inside ask() in app.py and nowhere else.

Docs: LangChain integration. Work from the docs first; the answer is below.

  1. Import the handler.
  2. Create it inside ask(), so each question gets its own.
  3. Pass it to graph.invoke(...) through config.
Done when: python app.py "<a question>" still answers.
Reference answer: the code
from langchain_core.runnables.config import RunnableConfig
from splunk_ao.handlers.langchain import SplunkAOCallback

def ask(graph, request: str, user_id: str = USER_ID) -> dict:
    callback = SplunkAOCallback(flush_on_chain_end=True)
    config = RunnableConfig(callbacks=[callback])
    return graph.invoke({"request": request, "user_id": user_id}, config=config)

Line by line

LineWhat it does and why
SplunkAOCallback(...)The SDK's LangChain/LangGraph handler. LangGraph reports every node, model call and tool call to it, and it builds them into one trace tree. No spans to write by hand.
Created inside ask()Each top-level invocation starts a new session and trace, so one question is one trace. It's in ask() because app.py and run_batch.py both use it, so all traffic is traced.
flush_on_chain_end=TrueSends the trace as soon as the run finishes. Without it, a short python app.py "..." can exit before the buffered trace is sent.
config=configPassing the config is what turns tracing on. Before, it was a bare graph.invoke({...}).
Nothing in agent/ changes LangGraph hands the callback to every node, so the four steps, tools and model calls are all traced from this one place.

  3. dealer_id needs a field on each shopper record in data.py.
Done when: a trace in the console shows your metadata.
Reference answer: the code

In data.py, give each shopper a dealer:

RECORDS = {

In app.py, add import data at the top and extend the config:

config = RunnableConfig(
    callbacks=[callback],
    metadata={
        "business_unit": os.getenv("BUSINESS_UNIT", "dealer-web-chat"),
        "dealer_id": data.RECORDS.get(user_id, {}).get("dealer_id", "unknown"),
        "shopper_id": user_id,
        "model": os.getenv("OPENAI_MODEL", "gpt-4.1-mini"),
        "failure_mode": mode(),
    },
    tags=["auto-retail"],
)

business_unitBUSINESS_UNIT env, default dealer-web-chat (an assumption)Spend and governance per business unit
dealer_iddata.RECORDS[user_id]["dealer_id"]Group by dealer site

State your assumptions at the readout: the business_unit default is made up, dealer_id means the dealer site the shopper is on, and model means the LLM, not the vehicle model.

Common mistakes
  • Two statements merged on one line (...SplunkAOCallbackcallback = ...), or code outside ask() because of missing indentation. Python can't parse it.
  • Using data.RECORDS without import data, which raises NameError.
  • Creating the callback once at the top of the file. Then every question shares one trace.

Reference answer: what to check in the console
  • One trace per question, with a tree under it: intake, route, resolve and write steps, the model calls inside them, and a tool call on the action path.
  • Your five metadata keys on the trace, and the auto-retail tag.

8. Instrumentation notes

Answer four questions in your own words, two or three sentences each. Keep them with your worksheet as readout/instrumentation-notes.md. Your coach will ask about them.

  1. Where does a trace start and end in your agent, and why there?
  2. Which parts of a run became which kind of span, and why?
  3. What metadata did you attach, and which customer question does it answer?
  4. What would you see in the console if you had instrumented only the model call?
Reference answers

1. Where does a trace start and end?

It starts when ask() calls graph.invoke(...) and ends when the graph returns the reply, so one shopper question is one trace. The callback is inside ask() because every question goes through it. A trace per model call would split one question across several traces, and the customer couldn't follow a question from request to reply. flush_on_chain_end=True sends the trace when the run ends.

2. Which parts became which spans?

I wrote no spans by hand. The callback reports what LangGraph does: the four steps, each model call inside them, and the tool call on the action path, as a tree under one trace. That matters here because the failure sits between the brochure lookup in resolve and the writer, so the customer can see which step handed the writer the bad claim. Check the exact span kinds and names in the console.

3. What metadata, and what does it answer?

Five keys. business_unit and model answer the buyer's interest in spend and governance. failure_mode separates clean from failure traffic, which supports the answer to "is this calibrated?". shopper_id and dealer_id find one conversation and group by dealer site. The business_unit default and the meaning of dealer_id are assumptions.

4. Only the model call instrumented?

I'd see model calls with prompts and replies, but no tree: no steps, no tool calls, and nothing tying calls into one shopper question. I could see the false claim but not whether the lookup, the routing or the writer caused it. Per-request cost would also be harder to attribute.

9. Build the custom judge

A custom LLM-as-a-judge evaluator that checks every claimed feature against the vehicle's inventory record. This is the win condition for the scenario.

Before you start LLM-judge evaluators need a model integration on the org. If the model picker is empty or errors, that's the org, not you. Ask the facilitator.
  1. Main menu, Evaluators, Create evaluator, LLM-as-a-judge.
  2. Fill in the settings and paste the prompt (below).
  3. Open Test Evaluator and run it against recent logged traces or spans.
  4. Open your stream, Configure Evaluators, switch your evaluator on, Save and close.
  5. Send fresh traffic. Only traces sent after you enable it get scored.
Done when: clean runs score true and failure runs score false with a rationale naming the brochure claim.

Prompt: give a clear rubric ("Set true if... Set false if...") and don't add response-format instructions.

You are an impartial evaluator checking a car-shopping assistant for grounding.

The input contains the shopper's question, marketing brochures, and the inventory record for the specific vehicle.
The output is the assistant's reply to the shopper.

Task: Determine whether every vehicle feature the reply says the vehicle has is listed in the inventory record for that vehicle. A feature mentioned only in a brochure does not count.

Set true if every claimed feature is listed in the inventory record, or the reply makes no feature claims.
Set false if the reply claims any feature that the inventory record does not list, or that the inventory record says is missing.
If it also scores the intake and route calls Use evaluator filters: on Configure Evaluators, use the action menu next to the evaluator, Apply filter, and match on span name or span metadata. Check the writer span's name in a trace first.
Be honest about two things
  • Don't call the judge calibrated. Calibration needs the customer's human-labeled examples. You can test the judge against a labeled dataset and report a macro F1 score.
  • The judge runs on the workshop's model, not the customer's. Say so if asked whose model is scoring.

1. Initialize once per process (app.py)

_control_ready = False

def init_agent_control() -> None:
    global _control_ready
    if _control_ready:                       # run_batch.py calls ask() many times
        return
    import agent_control
    from splunk_ao.logger import SplunkAOLogger

    logger = SplunkAOLogger(
        project=os.environ["SPLUNK_AO_PROJECT"],
        agent_stream=os.environ["SPLUNK_AO_AGENT_STREAM"],

    if logger.agent_stream_id is None:       # fail loudly, a control bound to nothing never fires

        agent_name=os.environ["AGENT_CONTROL_AGENT_NAME"],
        agent_description="Auto-retail car-shopping assistant",
        server_url=os.environ["AGENT_CONTROL_URL"],
        api_key=os.environ["AGENT_CONTROL_API_KEY"],
        api_key_header=os.environ.get("AGENT_CONTROL_API_KEY_HEADER", "Splunk-AO-API-Key"),
        target_type=os.environ.get("AGENT_CONTROL_TARGET_TYPE", "log_stream"),
        target_id=logger.agent_stream_id,    # the stream's ID, NOT its name
    )
    _control_ready = True

2. Decorate the writer's model call (agent/nodes.py)

from agent_control import control, ControlViolationError

@control(step_name="write-reply")
def _draft_reply(system: str, user_text: str) -> str:
    return llm(0.3).invoke([SystemMessage(system), HumanMessage(user_text)]).content

BLOCKED_REPLY = ("I want to be sure I give you accurate details on that feature, so I've passed your "
                 "question to a dealership specialist who will confirm it from the vehicle's inventory record.")

def write(state):
    ...
    try:
        reply = _draft_reply(system, f"Request: {state['request']}\n\n{context}")
    except ControlViolationError:
        return {"reply": BLOCKED_REPLY}      # never show the blocked text
    ...

Gotchas we hit

SymptomCause and fix
agent_name must be at least 10 characters longThe name was agent-${INSTANCE} and INSTANCE was undefined, so it became agent-. Set a real name.
Control never fires; reply has the false claimCheck the loaded control. Scope was tool steps, and the writer is an LLM step. Change Applies to to LLM.

Value shows with quotes in the consoleIf the loaded value prints as ['"BR-999"'] the quotes are part of the string, and it won't match. ['BR-999'] is correct. The console may display quotes without storing them.

Two similar controls loadedRe-adding made a clone. Remove the one you don't need so edits aren't made twice.
It fails closed If Agent Control returns an error, the SDK blocks the reply, so every question fails, not just matching ones. That is safe but worth stating at the readout.

12. Validate clean vs failure

Prove the failure gets caught and stopped, and that clean traffic is left alone.

  1. Send clean traffic: FAILURE_MODE=none python run_batch.py 10. Nothing should flag.
  2. Send the failure: FAILURE_MODE=fabricated_citation python run_batch.py 5, plus the targeted question a few times.
  3. In the console, confirm the judge flags the failure traces and its rationale says why.

The objection

They will say: "We already have LangFuse and a judge we calibrate by hand. We've seen these functions."

We answer: We're not replacing LangFuse; developers keep it for tracing. This sits next to it: your judge's definition of a bad answer runs on every trace, the failure is stopped before the shopper sees it, and someone is told. We can check the judge against your human-labeled examples to answer "is it calibrated" with your data.

Not ours

Improving the brochure-to-inventory data sync, which is where the bad claim comes from, belongs to the dealer-management-system team.

Check before you say it Don't present a criterion you haven't verified in the console: the alert firing, the business_unit filter, the judge scoring blocked runs.

Ten minutes as the customer meeting. Coaches play the roles and ask the quoted questions. Three screens, each tied to a real quote, then your success criteria. Then five minutes of feedback.

Likely questions

  • Is the judge calibrated? Not yet, and we don't claim it is. It uses your definition, shows a rationale on every score, and we'd compare with your human labels.
  • Why a custom judge, not a built-in evaluator? The failure is customer-specific: a feature missing from this vehicle's inventory record. A built-in evaluator doesn't know your inventory.
  • Why a control and an alert? The control stops this specific failure. The alert tells a person it happened.
  • Whose model scores this? The workshop's model through a gateway. In production you'd choose.
  • What if the control service is down? The SDK fails closed and blocks the reply, which is safe but means every question fails. Decide whether that's what you want.

Do not

  • Open with the agent graph, or spend more than two minutes on the agent.
  • Attack LangFuse.
  • Claim tokenomics attributes cost per agent or per trace.
  • Say the judge is calibrated.

15. What coaches look for

There are no scores. Coaches give feedback on the spot, using four questions in this order.

  1. Does every screen trace back to the customer? Which quote does each screen answer? A screen with no quote behind it is a platform tour.
  2. Are the evaluators and the control the right ones, and can you say why? Luna versus LLM-judge should be a deliberate choice. If the planted failure wasn't caught, what would have caught it?
  3. Would the customer agree with the success criteria? Three to five, in their words, each with how it's proven, plus the objection and the answer. Any criterion the customer never asked for gets pointed out.
  4. Can you explain every setting and every line you wrote? Two settings and one line of instrumentation are picked at random.

Things a coach calls out

  • More than two minutes of the readout spent on the agent itself.
  • A skeleton that grew past four steps or four tools.
  • Claiming the product does something the scenario's traps say it doesn't.
  • Attacking the incumbent instead of answering the objection.
Reference answer: prepare for the random picks
  • Settings: why flush_on_chain_end=True; why the judge applies to an LLM span; why the control is Post stage, LLM step, contains, deny; why BR-999 and not hands-free.
  • A line: config=config in graph.invoke is what turns tracing on; target_id=logger.agent_stream_id binds the control to the stream by ID, not name.
  • End with one sentence: the single thing you'd do differently on your next real customer.

Stretch: experiments and a UI

Beyond the required steps. Use them if you have time.

Test the judge against labeled examples

This answers "is this calibrated?" with a number. It's a dataset test on the evaluator, not a full experiment.

  1. Build a labeled dataset. Each row needs input, generated_output and Evaluator Ground Truth: what the judge should return. Replies citing only BR-002 are true; the failure replies citing BR-999 are false. Add tricky ones, such as a true answer that mentions "hands-free".
  2. Upload it under Datasets, Create Dataset (CSV or JSON) and map the columns.
  3. Run the test on your evaluator through the Test Evaluator tab's dataset option. It reports a macro F1 score and aligned and misaligned rows.
  4. Record the score, and rerun it after any change to the prompt, model or number of judges.
One catch Dataset testing works for trace or LLM-span evaluators. The judge reads the inventory record from the writer's prompt, so each row's input must include that context, not just the question.

Run the whole agent over a dataset

Use run_experiment(...) with function= pointing at your agent to compare models, prompts or a fix, with one trace per dataset row. Your questions.txt is already a dataset. It needs an LLM integration.

Needs a code change first The docs say app code called from an experiment must not start its own trace or flush it. ask() creates its own callback with flush_on_chain_end=True, so it would need to use the experiment's logger instead (splunk_ao_context.get_logger_instance()). Read the "Get an existing logger" section of Run Experiments in Code first.

A chat UI

It adds a shopper dropdown and a failure-mode dropdown, and shows when the control blocked a reply. Keep it out of the readout beyond triggering traffic, since time on the agent itself counts against you.
